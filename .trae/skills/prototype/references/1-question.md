# /prototype — Phase 1: 定义问题

> `/prototype` 的一部分。`SKILL.md` 规定了何时阅读本文件；它已解析的设置以及
> 其后续标题下的规则在这里同样适用。

## Phase 1: 定义问题

每次 `AskUserQuestion` 调用都遵循 `.claude/docs/automation-modes.md`
（协作模式总是询问 · 引导模式仅询问重大事项 · 自主模式记录并继续；
`automation_always_ask` 类别总是弹出提示）。

**检查 spike 模式：** 如果传入了 `--spike`，跳到本技能底部的 **Spike 模式** 部分。

**检查是否有结转笔记：** Glob `prototypes/*/PIVOT-NOTE.md`。如果存在针对该概念
（或其早期版本）的笔记，请阅读它，并从其修订后的假设开始，而不是从头构建假设——
说明你使用了哪份笔记。

随后，除非 `--spike` 已把你送到 Spike 模式，使用 `AskUserQuestion` 在继续之前
确认意图——无论是否有结转笔记：

- **提示**：“你想如何使用这次原型会话？”
- **选项**：
  - `Prototype this concept` — 构建一个一次性构建，在编写 GDD 之前验证核心想法是否有趣（最多 1 天）
  - `Skip — concept already proven` — 我已有足够证据表明它可行；记录下来并直接进入设计
  - `Mid-production spike` — 我已进入制作阶段，想快速测试某个具体机制或技术问题（约 4 小时，不涉及阶段闸门）

**如果选择“Skip — concept already proven”：**
询问（纯文本，而非组件）：“你有什么证据表明这个概念可行？”
记录这一行回答，然后停止。注明：“Concept prototype skipped — evidence:
[answer]。” 建议下一步：`/map-systems` 或 `/design-system [mechanic]`。

**如果选择“Mid-production spike”**：跳到下面的 **Spike 模式** 部分。

**如果选择“Prototype this concept”**：继续下面的 Phase 1。

---

**关于原型策略的说明：** 关于成功独立游戏开发的研究结论是一致的——构建 2-3 个
概念变体并让最好的那个胜出，远比把一个概念迭代到能用来得更容易成功。这是你的
第一个原型，不一定是唯一的原型。如果这个原型得出 PIVOT 结论，请考虑是改进这个
概念，还是围绕同一游戏想法换一个角度重新开始并原型化那个新方向。

**把 Game Jam 作为原型载体：** 如果你本来就打算做概念原型，考虑安排到 game jam
（Ludum Dare、GMTK Game Jam、Global Game Jam）期间进行。Game jam 提供了强制的
时间盒（48-72 小时）、向成千上万会评分并评论早期构建的玩家即时分发，以及一个从
设计上防止范围蔓延的截止期限。许多已发行的游戏（Celeste、VVVVVV）最初都是 jam
原型。这不是必须的——但如果时机合适，值得考虑。

从参数中读取概念描述。在构建任何东西之前，定义这个原型必须回答的**可证伪假设**：

> *“如果玩家 [做 X]，他们会感到 [Y]——如果 [可测量的信号 Z]，我们就知道这是真的。”*

好的例子：“如果玩家在抓钩上摆荡，移动穿越会感觉流畅——如果玩家在拿到它 2 分钟内
不停顿地连续 3 次以上摆荡，我们就知道成立。”

坏的例子：“这好玩吗？” ← 不可测试，不可证伪。

**如果概念过于模糊、无法形成假设，就停在这里。** 请用户先收窄问题再继续。没有明确
问题的原型只会浪费时间。

同时询问：**“这个概念中风险最高的假设是什么？”** 这是原型首先要测试的东西——不是
最容易的部分，而是风险最高的部分。
