## Phase 3: 选择原型路径

**本文件内容：**

- 路径：HTML（浏览器可玩）
- 路径：引擎（引擎工程）
- 路径：纸面（规则文档 + 试玩记录）

选择原型路径。如果传入了 `--path [html|engine|paper]`，就使用该值。
否则，先使用下面的速查表，然后阅读下方的完整路径细节：

| 类型 | 推荐路径 | 关键原因 |
|-------|-----------------|------------|
| 平台跳跃 / 动作 / 格斗 | **引擎** | 手感就是假设；浏览器延迟会产生错误结果 |
| 竞速 / 体育 | **引擎** | 同上——时机与物理反馈才是重点 |
| 俯视角射击 / 双摇杆 | **引擎** | 瞄准手感对时机敏感 |
| 解谜（逻辑） | **HTML** 或 **纸面** | 时机不是重点；逻辑与清晰度才是 |
| 卡牌游戏 | 先 **纸面** | 在碰代码之前用手工迭代最快 |
| 叙事 / 视觉小说 | **纸面**（Twine / Ink / Yarn Spinner） | 故事就是机制——无需代码开销即可测试 |
| 策略 / 4X / 城市建造 | **纸面**（电子表格模拟） | 在构建之前验证经济与进度规则 |
| Roguelike（系统繁重） | **纸面** → 引擎 | 在构建之前验证规则集是否有趣 |
| 放置 / 点击 / 增量 | **HTML** | 回合制逻辑，不需要手感敏感度 |
| 音游 | 先 **纸面**（用音频设计关卡） | 在引擎存在之前先设计关卡 |
| RPG / 开放世界 | **纸面** → 引擎 | 系统复杂度高：先验证规则，再验证手感 |
| 恐怖 / 氛围 | **引擎** | 氛围需要真实渲染 |

**经验法则：**“这个手感对吗？” → 引擎。“这些规则有趣吗？” → 纸面。“这个逻辑正确吗？” → HTML 或纸面。

### 路径：HTML（浏览器可玩）

**最适合：** 解谜游戏、卡牌游戏、回合制策略、文字游戏、放置游戏、
俯视角逻辑游戏。任何不依赖时机精度的内容。

**可靠性：** 一次性成功约 85–90%。agent 编写一个自包含的 HTML 文件，
用户在浏览器中打开——无需安装。

**局限——浏览器延迟会歪曲游戏手感。** 浏览器会引入 50–133ms 的渲染波动。
这使得 HTML 原型从根本上不适合动作游戏、平台跳跃游戏、格斗游戏，或任何你正在
测试输入时机、跳跃弧线或碰撞手感的内容。如果假设是手感，请改用引擎路径。

**此路径的替代工具：** PICO-8（极端约束，非常适合复古街机概念，一条命令即可导出
网页）、Phaser.js（能力更强的浏览器游戏框架，同样无需安装）或 Twine（叙事/选择
驱动的游戏）。对于各自对应的类型，它们比原生 HTML 更快——在合适时推荐它们。

**产出：** 一个 `prototype.html`（或 PICO-8/Phaser 等价物），用户可在任意浏览器中打开。

**分发——HTML 路径最大的优势：** 与引擎原型不同，这个构建可以在几分钟内触达全球
真实玩家。请积极利用：
- **itch.io**——上传文件、分享链接，几小时内即可获得游玩次数和书面反馈。免费。
  独立社区会在这里玩粗糙的构建，并不期待打磨。这是零成本的真正外部验证。
- **Loom + 文件共享**——通过 Google Drive/Dropbox 分享，请某人在游玩时用 Loom
  录制屏幕 + 音频。你无需同步安排，就能得到真实第一印象反应与困惑的视频。
- **r/playmygame 或 r/WebGames**（Reddit）——专门测试早期构建并主动给出诚实反馈的
  活跃社区。
- **游戏开发 Discord 服务器**（GMTK、Brackeys、GameDev.tv）——成员经常互相测试
  原型；HTML 文件是最容易提出的请求。

### 路径：引擎（引擎工程）

**最适合：** 动作游戏、平台跳跃游戏、物理繁重的游戏，任何即时手感就是假设的内容。
当 HTML 延迟会歪曲结果时使用它。

**可靠性：** 一次性成功约 50–60%。预计需要 2–4 轮迭代——这是正常的，不是失败。

**局限——需要已安装并运行的引擎。** 此路径是一个多轮协作循环：
1. agent 编写代码
2. 用户在引擎中运行
3. 用户报告错误或观察结果
4. agent 修复并迭代

**沉没成本规则：** 如果用户已经迭代超过 2 小时仍未达到可玩状态，就停下。范围太大
或问题错了。重新表述假设并大幅简化，或者切换到纸面路径。

**产出：** 位于 `prototypes/[name]-concept/` 中的最小可运行引擎工程。

**更轻量的替代——Love2D（Lua）：** 如果项目引擎（Godot、Unity、Unreal）对于一次性
构建来说过于笨重，可以考虑 Love2D——一个极简的 2D 框架，几分钟即可安装，无需工程
脚手架，原生渲染且没有浏览器延迟。许多独立开发者用它快速制作 2D 动作与平台跳跃
原型（Balatro 用 Love2D 原型化；Nuclear Throne 的早期构建也使用了它）。它介于 HTML
开销和完整引擎开销之间：比打开浏览器重，比搭建完整引擎工程轻。当项目引擎偏向 3D
或需要较长时间配置时，它最适合 2D 动作/平台跳跃的手感验证。

### 路径：纸面（规则文档 + 试玩记录）

**最适合：** 策略游戏、卡牌游戏、桌游风格机制、经济系统、进度循环，任何逻辑可以用
手工模拟的游戏。当你需要验证规则而非手感时，适用于任何类型。

**可靠性：** 100%。无代码、无引擎、无安装。

**局限——无法验证即时手感。** 纸面原型能证明规则内部一致、决策有趣。它们无法告诉
你跳跃手感是否正确，或者爆炸是否令人满足。

**纸面试玩观察协议（与 5 人以上一起执行）：**
1. 只讲解一次规则。把规则摘要单递给他们。然后退后。
2. 不要进一步解释。不要帮忙。不要澄清。困惑就是数据。
3. 安静观察。记录他们每一次放慢、重读或提问的时刻。
4. 结束后只问一个问题：“哪里让你困惑？”——而不是“你喜欢吗？”
5. 每次迭代都使用新的测试者。同一个人无法提供新的第一印象数据。
6. 如果 3 个以上测试者在同一困惑点卡住，那条规则就是坏的——重新测试前先重新设计它。

**产出：** 一份可打印的规则文档 + 一份展示一次模拟会话的完整试玩记录。

**此路径的叙事工具：** 对于对话繁重和故事驱动的游戏，跳过通用规则文档——改用专用的
叙事脚本工具：
- **Twine** ——零代码超文本小说；非常适合分支结构实验和选择影响测试
- **Ink**（Inkle）——用于 *80 Days*、*Heaven's Vault* 和 *Overboard* 的纯文本脚本语言；可直接导出到 Unity 和 Godot
- **Yarn Spinner**——用于 *A Short Hike*、*DREDGE* 和 *Night in the Woods* 的对话脚本；原生集成 Unity 和 Godot

这三种工具都能让你在几分钟内编写并试玩分支对话。叙事原型的关键指标：
**首次情感触点所需时间**——玩家在多少次交流后才有所感受？如果需要超过 3-4 次交流，
开场就太慢了。

评估哪条路径最契合假设，然后使用 `AskUserQuestion` 并预先陈述你的推荐：

- **提示**：“你想使用哪条原型路径？（根据你的概念，我推荐 [path]——[一句话理由]。）”
- **选项**：
  - `HTML — browser prototype` — 解谜、卡牌、回合制、策略、放置。双击即可打开，无需安装。85–90% 可靠。**不适合动作游戏**——浏览器延迟会歪曲手感。
  - `Engine — native prototype` — 动作、平台跳跃、物理，或任何手感就是假设的内容。一次性成功 50–60%；2–4 轮迭代属正常。需要已安装引擎。
  - `Paper — rules document + play log` — 策略、经济、逻辑、桌游风格机制。100% 可靠。无法验证手感。
