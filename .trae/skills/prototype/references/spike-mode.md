# /prototype — Spike 模式

> `/prototype` 的一部分。`SKILL.md` 规定了何时阅读本文件；它已解析的设置以及
> 其后续标题下的规则在这里同样适用。

**触发方式：** `--spike` 标志，或 Phase 1 中选择“Mid-production spike”入口。

**目的：** 在制作中期测试某个具体的技术或设计问题，无需承担完整概念原型工作流
的开销。没有 GDD 前置条件。不涉及阶段闸门。硬性上限：约 4 小时。

**何时使用：**
- 你已在制作阶段，想测试是否应该加入某个新机制
- 在正式构建前，你不确定某种技术方案是否可行
- 正在考虑一项设计变更，想要快速的前后对比
- 某个 GDD 系统比预期更难，你想把困难的部分做成原型
- 在编写玩法代码之前，你需要确认目标硬件能维持所需帧率（**性能 spike**——见下文）

**Spike 模式工作流（替代 Phase 1–9）：**

1. **定义 spike 问题**（纯文本，不用组件）：“这个 spike 要回答什么具体问题？给我一句话：‘我们能使用 [方案 Y] 实现 [做 X] 吗？’”

2. **选择路径**——与 Phase 3 相同的 AskUserQuestion 组件（HTML / 引擎 / 纸面）。

3. **范围**——最多 2-3 个要点。一个机制，一个技术问题，别无其他。

4. **构建**——先询问“我可以创建 `prototypes/[concept-name]-spike-[date]/` 并在其中构建 spike 吗？” 同样放宽的标准和头部，与概念原型一致。硬性上限：4 小时。如果 4 小时内无法演示，问题就太大了。拆分它。

5. **观察并决定**——不做正式试玩复盘。询问：“spike 回答那个问题了吗？YES 或 NO，并一句话说明原因。”

6. **写一份 spike 笔记**（不是完整报告）到 `prototypes/[concept-name]-spike-[date]/SPIKE-NOTE.md`——先为这一步和下一步一次性询问，并点明两个文件：“我可以写入 `prototypes/[concept-name]-spike-[date]/SPIKE-NOTE.md` 并从 `production/session-state/active.md` 中清除该 spike 吗？” 笔记包含：
   - 测试的问题
   - 结果（YES 可行 / NO 不可行 / PARTIAL——需要进一步调查）
   - 下一步做什么（加入当前冲刺——在 `workflow: minimal` 下，即简报的构建顺序—— / 进一步调查 / 放弃该想法）

7. **更新 `production/session-state/active.md`**，清除该 spike 并回到当前冲刺状态（在 `workflow: minimal` 下，即进行中的用户故事）。

**没有 CD 闸门。没有阶段闸门。没有 PROCEED/PIVOT/KILL。** Spike 结果为决策提供信息；它们不替人做决策。开发者根据 spike 揭示的内容，决定是否把该机制/方案加入冲刺待办列表（在 `workflow: minimal` 下，加入简报的构建顺序）。

**性能 spike（特殊情况）：** 如果游戏涉及高负载渲染——
大型开放世界、数百个同时存在的物理刚体、繁重的粒子系统、
复杂着色器——在编写玩法代码之前运行一次性能 spike，以确认
目标硬件能维持所需帧率。它与其他 spike 有两点不同：
- 问题是“引擎能在 [最低配置硬件] 上以 60fps 渲染 [场景 X] 吗？”
  而不是“这个机制手感好吗？”
- 产出是一个基准数字，而不是手感结论
- 不需要玩法逻辑——只需要最大预期场景负载（地形、绘制调用、
  物理对象、粒子）同时运行
- 构建时间保持在约 4 小时上限内；spike 是在搭建渲染负载，
  而不是游戏
- 如果在这个范围内答案是 NO，这就是一个影响所有下游的架构或范围约束
  ——最好现在就暴露它，而不是等到 Sprint 8
