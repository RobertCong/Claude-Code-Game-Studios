# /setup-engine — 第 5.5 节：填充 project.yaml

> 属于 `/setup-engine` 的一部分。`SKILL.md` 指明何时读取本文件；它解析出的
> 设置及其后续标题下的规则在此仍然适用。

## 5.5 填充 `project.yaml`（主配置存储）

**本文件内容：**

- 5.5.1 构建四个块
- 5.5.2 将块写入 `project.yaml`
- 5.5.3 验证双写

> **v1.1：** 仓库根目录的 `project.yaml` 是项目配置的**主**存储。
> 第 5 节写入的 `.claude/docs/technical-preferences.md` 作为**旧版镜像**保留，
> 用于向后兼容。本步骤是**双写** — 相同的引擎事实写入两个文件，
> 当某个技能读取的键在两个文件中都存在时，以 `project.yaml` 为准。

在 `technical-preferences.md` 写入并获批之后，将结构化配置双写到 `project.yaml`。
共写入四个块：`engine`、`specialists`、`naming` 和 `commands`。

### 5.5.1 构建四个块

每个值都从第 3–4 节已选定的引擎和语言推导。不要重新询问
**引擎、版本或语言** — 复用那些决定。

> **这并不是一条"绝不询问"的一刀切规则。** 下面的 `rendering` 和 `physics`
> 依赖另外两个输入 — 目标平台和 2D 还是 3D — 而**第 2 节只在四条入口路径中的
> 一条上收集它们**。如果从未收集过，就询问；项目形态表下方的
> 不可用分支说明了如何询问。

**`engine` 块：**

```yaml
engine:
  name: "<Godot|Unity|Unreal>"
  version: "<version from Section 3>"
  language: "<GDScript|C#|C++|Blueprint>"
  rendering: "<engine default — see table>"
  physics: "<engine default — see table>"
```

**在 Godot 上，这两个值取决于第 2 节已经收集的答案 —
目标平台和 2D 还是 3D — 因此不要仅凭引擎名称来选择它们。**
在 Unity 和 Unreal 上，表中只有一行 `any`，引擎名称*就*足够了；
直接采用那些行。

| 引擎 | 项目形态 | `rendering` 默认值 | `physics` 默认值 |
|--------|---------------|---------------------|-------------------|
| Godot 4.x | 2D · web target | Compatibility | Godot Physics 2D |
| Godot 4.x | 2D · non-web | Forward+ | Godot Physics 2D |
| Godot 4.x | 3D · web target | Compatibility | Jolt |
| Godot 4.x | 3D · non-web | Forward+ | Jolt |
| Unity | any | URP | PhysX |
| Unreal | any | Lumen + Nanite (deferred) | Chaos |

> **为什么 Godot 的行取决于项目形态。** 如果仅凭引擎名称选择，
> 两个 Godot 默认值对 2D 浏览器游戏都是错的。
> - **Jolt 是 Godot 的默认 *3D* 引擎。** `docs/engine-reference/godot/modules/physics.md`：
>   "Jolt Physics is the DEFAULT 3D engine" 以及 "2D physics UNCHANGED (still
>   Godot Physics 2D)"。在 2D 项目上写 `Jolt`，会让实现者去
>   调优其游戏根本不使用的后端。
> - **Forward+ 面向桌面端。** `docs/engine-reference/godot/modules/rendering.md`：
>   Forward+ 是 "Full featured, desktop-focused"；Compatibility 是
>   "OpenGL 3.3 / WebGL 2, broadest hardware support" — 浏览器路径。
>
> 如果第 2 节的平台答案是 `Multiple platforms` 且**包含** Web，
> 则使用 Web 行：渲染器必须在游戏发布的所有平台上都能工作。

> **仅限 Godot — Unity 和 Unreal 各只有一行，键为 `any`。** 对这两个引擎，
> 形态无法改变 `rendering` 或 `physics`，因此**不要**为它们执行下面的
> 解析流程：向操作者询问一个其答案会被丢弃的问题，恰恰是 §5.5.1 开头所禁止的。
> 在 Unity 上直接按表写入 `URP`/`PhysX`，在 Unreal 上直接写入
> `Lumen + Nanite (deferred)`/`Chaos`。
>
> **第 2 节未必运行过 — 读取其答案之前先检查。**
> 目标平台和 2D 还是 3D 是在*问题 2–6 下、且仅当没有先前的引擎经验时*收集的。
> **四条入口路径中有三条永远不会到达这些问题：**
> `/setup-engine <engine> <version>` 和 `/setup-engine <engine>` 会直接跳过第 2 节，
> 而引导模式一旦用户说出自己用过的引擎，就会跳过矩阵。只有引导模式回答 `None` 或 `Multiple`
> 时才会同时收集这两项。
>
> 按以下顺序解析每个输入，并在第一个能给出答案的来源处停止：
> 1. **第 2 节的答案**，如果该路径运行过。
> 2. **设计产出物** — `standard`/`full` 层级为 `design/gdd/game-concept.md`，
>    `minimal` 层级为 `design/game-brief.md`。第 2 节已从这些文件提取平台
>    目标；如果其中说明了 2D 还是 3D，也以同样方式提取。
> 3. **询问。** 不要从引擎名称推断形态，也不要写入
>    你无法证明的行：
>    - 提示："`rendering` 和 `physics` 取决于项目形态，而这一点
>      尚未确定。这是 2D 还是 3D，是否会发布到 Web？"
>    - 选项：`2D · non-web` / `2D · web` / `3D · non-web` / `3D · web`，加上
>      `Leave as [TO BE CONFIGURED]` — 在这里这是合理的答案，待概念存在后
>      可通过 `/settings` 重新设置。
>
> `[TO BE CONFIGURED]` 是两个键都有效的值。在 2D 项目上写错 `Jolt`
> 比不设置更糟，因为下游没有任何东西会质疑它。

- `rendering` 和 `physics` 是引擎的典型默认值 — 告诉用户，如果项目使用不同的设置，
  之后可以通过 `/settings` 更改。
- 对于 Godot **Both**，写入 `language: "GDScript"`（主要玩法
  语言）；C# 的使用情况记录在 `technical-preferences.md` 中。
- 对于 Unreal，写入 `language: "C++"` — 或者仅当项目以 Blueprint 为主时
  写入 `"Blueprint"`。Blueprint 作为辅助工具不会改变此值。

**`specialists` 块** — 直接复制第 5 节中选择的路由表
（Godot 见 `references/godot-language-config.md` 中的 **A3**）：

| 引擎 / 语言 | `code` | `shader` | `ui` | `additional` |
|-------------------|--------|----------|------|--------------|
| Godot — GDScript | godot-gdscript-specialist | godot-shader-specialist | godot-specialist | [godot-gdextension-specialist] |
| Godot — C# | godot-csharp-specialist | godot-shader-specialist | godot-specialist | [godot-gdextension-specialist] |
| Godot — Both | godot-gdscript-specialist | godot-shader-specialist | godot-specialist | [godot-csharp-specialist, godot-gdextension-specialist] |
| Unity | unity-specialist | unity-shader-specialist | unity-ui-specialist | [unity-dots-specialist, unity-addressables-specialist] |
| Unreal | unreal-specialist | unreal-specialist | ue-umg-specialist | [ue-gas-specialist, ue-blueprint-specialist, ue-replication-specialist] |

```yaml
specialists:
  code: "<code specialist>"
  shader: "<shader specialist>"
  ui: "<ui specialist>"
  additional: ["<...>"]
```

**`naming` 块** — 枚举值（不是 `technical-preferences.md` 中使用的
散文形式）。使用与引擎匹配的列，对于 Godot，
还需匹配语言：

| 字段 | Godot GDScript | Godot C# | Unity | Unreal |
|-------|----------------|----------|-------|--------|
| `classes` | PascalCase | PascalCase | PascalCase | PascalCase |
| `variables` | snake_case | camelCase | camelCase | **PascalCase** |
| `constants` | SCREAMING_SNAKE | PascalCase | SCREAMING_SNAKE | SCREAMING_SNAKE |
| `signals` | past_tense | on_event_name | **PascalCase `On<Event>`** | **PascalCase `On<Event>`** |
| `files` | snake_case | PascalCase | PascalCase | PascalCase |
| `scenes` | snake_case | PascalCase | PascalCase | PascalCase |

> **Unreal 列有来源依据，并非继承自表格的通用形态。**
> `variables: camelCase` 和 `signals: on_event_name` 是那种形态会产生的两行，
> 而两者对 Unreal 都是错的。已对照本仓库固定的参考资料核查：
> `docs/engine-reference/unreal/` 包含**零**个 camelCase
> 变量声明，并且通篇使用 PascalCase（`int32 Health;`、
> `FVector ServerPosition;`），而 "signal" 一词**在其中从未出现** —
> 它是 Godot 的词汇。Unreal 有委托和事件，参考资料的
> 处理函数是 PascalCase `On<Event>`。
>
> 保留而非掩盖两点注意事项。(1) `classes: PascalCase` 对 Unreal 而言是
> **不完整的**，并非错误：UE 要求强制类型前缀
> （`U`/`A`/`F`/`E`/`I`/`T`），此枚举无法表达，因此 Unreal 项目的
> 编码标准必须单独说明。(2) `scenes` 是**类别不匹配** — Unreal 在 World Partition 下有
> 关卡（Level）和地图（Map），而非场景 — 保留原样是因为该键在各引擎间共享，
> 重命名它属于模式变更，而不是值修正。
>
> 影响范围有限：`naming.*` 目前是
> **有文档但未被读取**的设置，因此错误的值只会误导阅读
> `project.yaml` 的人，而不会驱动任何自动化检查 — 至少目前如此。这恰恰是
> 现在趁代价还小就把它们改对的原因。

> **此表还有三条规则。**
>
> **Unity 的 `build` 行不得硬编码 `-buildTarget StandaloneLinux64`。**
> 硬编码目标会让每个 Unity 项目都得到一条 **Linux** 构建命令，无论它
> 实际发布到哪个平台。该行应写 `<TARGET>`：**询问操作者
> 构建目标并写入他们给出的值。** 正确的 `-buildTarget` 标识符
> 无法从 `docs/engine-reference/unity/` 中获取，因此本技能不得
> 凭记忆生成 — 这与 `/security-audit` 的存档模式以及 Unity 的发布日期
> 的处理方式相同。错误但看似合理的默认值比
> 明确提问更糟：它会产生一条能运行、能成功、却构建出错误产物的
> `commands.build`。
>
> **仅 `-buildTarget` 本身不构建任何东西。** 它切换活动平台
> 然后以退出码 0 退出（已在 6000.3.23f1 上验证）。该行还需要一个播放器构建标志，
> `-build<PLATFORM>Player <output path>` — 对于 Windows 64 位，
> 为 `-buildWindows64Player Builds/Win64/<Game>.exe`（已验证：退出码 0 并生成
> `.exe`；编译错误或构建设置中没有场景时退出码为 1）。
> 询问是哪个平台，并对照 Unity 的命令行文档确认其他平台的标志，
> 而不是凭记忆写一个。
>
> **Godot 的 `build` 行同样不得硬编码 `'Linux/X11'` — 同样的缺陷，
> 同样的补救办法。** Godot 导出预设名称是**项目定义的**：它是操作者
> 在 `export_presets.cfg` 中键入的任意字符串，而随附默认值是
> 按平台的（`Windows Desktop`、`macOS`、`Web`、`Linux/X11`）。写入
> `'Linux/X11'` 会让面向 Windows 的项目得到一条构建命令，因
> `Unknown export preset` 而失败；而让*确实*有 Linux 预设的项目
> 悄悄构建错误平台。该行应写 `<PRESET>`：
> **询问操作者要构建哪个导出预设并写入他们给出的值**，
> 与 Unity 行的做法完全一致。如果尚无任何预设 — 这很常见，因为
> `/setup-engine` 通常在 Godot 项目还没有预设时运行 — 写入
> `[TO BE CONFIGURED]` 并说明这一点，而不是猜测一个不存在的名称。
>
> **`constants` 行不得与本技能自身的说明文字矛盾。** 表中对 Unity
> 写的是 `SCREAMING_SNAKE`；同一文件的 Unity 章节却说
> "Constants: PascalCase or UPPER_SNAKE_CASE"。两者不可能都是权威，而
> 遵循其中之一的 agent 会产生被另一方拒绝的配置。该行
> **在取得来源依据前保持原样**，而不是按偏好挑选 —
> `docs/engine-reference/unity/` 和 `unreal/` 都不包含可确认或反驳它的
> SCREAMING_SNAKE 常量，因此 Unreal 列的 `SCREAMING_SNAKE` 同样无来源依据。
> 解决方式是向引擎参考资料添加命名章节，然后同时修正表格和说明文字。
> 在此之前，将 Unity 和 Unreal 的 `naming.constants` 视为未经验证。
>
> **把那条注意事项写入 `project.yaml`，不要留在这里。** 在 Unity 和
> Unreal 上，输出 `constants` 行时附带行尾注释：
> ```yaml
> naming:
>   constants: SCREAMING_SNAKE   # UNVERIFIED — not sourceable from
>                                # docs/engine-reference/<engine>/; confirm before relying on it
> ```
> 否则，本技能*明知*无来源依据的值，会被记录得和
> `classes: PascalCase`（有来源依据）一样平实，主配置存储的读者
> 便无法区分两者。下面九行处的 `commands` 块已经通过其
> `# TODO: confirm these` 行这样做了 — 这是相同的模式，
> 应用于同样需要它的值。

对于 Godot **Both**，使用 GDScript 列 — `.gd` 文件主导玩法
脚本；`.cs` 文件按文件遵循 C# 约定（见 `references/godot-language-config.md` 中的 **A2**）。

```yaml
naming:
  classes: <value>
  variables: <value>
  constants: <value>
  signals: <value>
  files: <value>
  scenes: <value>
```

**`commands` 块** — 引擎默认 shell 命令，简单字符串形式：

| 引擎 | `build` | `test` | `run` | `smoke` |
|--------|---------|--------|-------|---------|
| Godot | `godot --headless --export-debug '<PRESET>'` **（询问 — 不要默认）** | `godot --headless -s -d --remote-debug tcp://127.0.0.1:0 res://addons/gdUnit4/bin/GdUnitCmdTool.gd -a res://tests --ignoreHeadlessMode` | `godot --path . --windowed --resolution 1280x720` | `godot --headless --quit-after 5` |
| Unity | `"<Unity editor>" -batchmode -quit -projectPath . -buildTarget <TARGET> -build<PLATFORM>Player Builds/<Target>/<Game>.exe` **（询问 — 不要默认）** | `"<Unity editor>" -batchmode -runTests -projectPath . -testPlatform EditMode -testResults test-results/editmode.xml` | `Builds/<Target>/<Game>.exe -screen-width 1280 -screen-height 720 -screen-fullscreen 0` | `"<Unity editor>" -batchmode -quit -projectPath . -logFile -` |

> **每个退出码证明了什么 — 每一行都已在固定版本引擎上验证。**
> Godot `test` 全部通过时退出 0，有失败时退出 100，全部通过但有
> 节点泄漏时退出 101（这是警告，不是失败），测试脚本无法
> 解析时退出 105，gdUnit4 完全无法运行时退出 103 / 104（无头模式被拒绝、
> Godot 低于 4.3）。保留 `--remote-debug tcp://127.0.0.1:0`：没有它，脚本
> 错误会打开 Godot 的交互式调试器，运行会永远停在 `debug>`
> 提示符处，而不是退出。在新克隆的仓库上，先运行
> `godot --headless --path . --import`：没有 `.godot/` 类缓存时，
> `GdUnitCmdTool.gd` 无法加载，运行会在什么都没跑的情况下以 1 退出。Unity `test`
> 退出 0 / 2，结果文件中出现 `testcasecount="0"` 意味着没有测试被
> 编译 — 不是通过。它只运行编辑模式：`Assets/Tests/PlayMode/` 下的
> 播放模式测试需要第二次运行并写入它们自己的结果文件
> （`-testPlatform PlayMode -testResults test-results/playmode.xml`），
> 只要该文件夹中有测试，`/smoke-check` 就会这样做，并且 CI 将其作为独立
> 步骤运行。Unity `smoke` 在编译错误时退出 1，干净时退出 0。
> **Godot `smoke` 即使在解析错误时也会退出 0** — 它是启动检查：读取其
> 输出中的 `SCRIPT ERROR`。它还需要设置 `run/main_scene`：没有主场景时，
> 它会打印 `Can't run project: no main scene defined` 且永不退出，因此要在
> 超时限制下运行。Unity `smoke` 只编译编辑器端的程序集；
> 仅存在于播放器构建中的错误（没有自己程序集的 `Editor/` 脚本）
> 会出现在 `build` 中，而不是这里。真正的 Godot 解析检查是
> `godot --headless --path . --import`，然后
> `godot --headless --path . -s res://.claude/scripts/godot-parse-check.gd -- res://<file>.gd …`
> （脚本无法加载时退出 1）。`--check-only` 不算：它会让引用了自动加载的
> 有效代码失败。`<Unity editor>` 是**编辑器**可执行文件的完整路径，
> 需加引号。绝不要写裸 `Unity`：在 `PATH` 中该名称
> 可能是 Unity 单独的 CLI，它会以退出码 2 拒绝 `-batchmode` — 与测试失败
> 相同的退出码。

> **`commands.run` 是运行并观察步骤所依赖的那一个。** 它必须
> 启动**游戏**，带窗口，使用固定分辨率 — 绝不是编辑器，
> 也绝不要使用无头 / 批处理 / null-RHI 标志，这些标志的存在就是为了跳过渲染。
> `/dev-story` 的 Phase 6 第 4 步会向它追加各引擎的捕获标志
> （`.claude/docs/run-and-observe.md`）。`smoke` 是 Unity 的解析检查，`test`
> 供 `/smoke-check` 使用；`build` 是你必须询问的那一行。

> **YAML 引号规则 — 适用于每一个命令值。** `yaml-helper.sh` —
> 本框架中每次配置读取都会经过的解析器 — **不**解码任何
> 转义序列：双引号标量中的 `\"` 和单引号标量中的 `''` 都不解码。
> 它把第一个匹配的引号字符视为值的结尾，并丢弃其余部分，
> 因此 `"he said \"hi\" now"` 会解析为 `he said \`。已针对解析器
> 验证，而非推断。该规则至关重要：`/smoke-check` 和 `/dev-story` 会运行这些值，
> `/settings` 通过此解析器读写它们，`project.yaml` 中所有其他
> 带引号的值同样如此。
> 选择**无需转义**的引号风格：
> - 值包含单引号 `'`（例如上面的 Godot `build`）→ 用
>   **双引号** YAML 标量包裹：`"... 'Linux/X11' ..."`
> - 值包含双引号 `"`（例如下面的 Unreal `test`/`smoke`）→
>   用**单引号** YAML 标量包裹：`'... "Quit" ...'`
> - 值两者都不包含 → 为保持一致，使用双引号标量。
> 绝不要使用强制转义的引号风格（`\"` 或 `''`）— 解析器
> 会在转义处截断值。同时包含两种引号的值无法为此解析器表示；
> 重写命令以去掉其中一种。

**Godot / Unity** — 直接写入表中的值，将 `<PRESET>` / `<TARGET>` / `<PLATFORM>`
替换为操作者的回答，将 `<Unity editor>` 替换为编辑器的完整路径。
Godot 的 `build` 包含单引号，因此
使用双引号标量（下面的 `Windows Desktop` 是*示例*答案，不是
默认值 — 写入操作者所说的内容）：

```yaml
commands:
  build: "godot --headless --export-debug 'Windows Desktop'"
  test: "godot --headless -s -d --remote-debug tcp://127.0.0.1:0 res://addons/gdUnit4/bin/GdUnitCmdTool.gd -a res://tests --ignoreHeadlessMode"
  run: "godot --path . --windowed --resolution 1280x720"
  smoke: "godot --headless --quit-after 5"
```

**仅当第 3 节的 `godot --version` 成功运行时才写裸 `godot`** — 也就是
`godot` 在 `PATH` 中。否则（Windows 和 macOS 上的常见情况）
用探测找到或用户提供的可执行文件替换 — Windows 的
`Godot_v<version>-stable_win64.exe`、macOS 的 `/Applications/Godot.app/Contents/MacOS/Godot`
— 将其完整路径放在双引号中，替换四个值开头的 `godot`，
与 `<Unity editor>` 的做法完全一致。此时值包含双引号，因此
使用单引号标量，而 `build` 也用双引号引用其预设，
所以没有值同时包含两种引号类型。Godot 不在 `PATH` 中，安装在
`C:/Program Files/Godot/` 下：

```yaml
commands:
  build: '"C:/Program Files/Godot/Godot_v4.7.2-stable_win64.exe" --headless --export-debug "Windows Desktop"'
  test: '"C:/Program Files/Godot/Godot_v4.7.2-stable_win64.exe" --headless -s -d --remote-debug tcp://127.0.0.1:0 res://addons/gdUnit4/bin/GdUnitCmdTool.gd -a res://tests --ignoreHeadlessMode'
  run: '"C:/Program Files/Godot/Godot_v4.7.2-stable_win64.exe" --path . --windowed --resolution 1280x720'
  smoke: '"C:/Program Files/Godot/Godot_v4.7.2-stable_win64.exe" --headless --quit-after 5'
```

如果探测未找到可执行文件，且用户不知道它在哪里，保留
裸 `godot`，在块上方写入 `# TODO: godot is not on PATH here — set the editor's full
path via /settings`，并说明这一点：在两者之一被修正之前，
这些命令都不会运行。

对于 Unity，探测 Hub 安装目录（Windows 上为
`C:/Program Files/Unity/Hub/Editor/<version>/Editor/Unity.exe`，
macOS 上为 `/Applications/Unity/Hub/Editor/<version>/Unity.app/Contents/MacOS/Unity`，
Linux 上为 `/home/<user>/Unity/Hub/Editor/<version>/Editor/Unity`）或询问。
写入展开后的绝对路径 — 引号内的 `~` 不会被展开，
命令随后会以 127 退出。带引号的路径会在命令中放入双引号，
因此该值使用单引号标量：

```yaml
commands:
  test: '"C:/Program Files/Unity/Hub/Editor/6000.3.26f1/Editor/Unity.exe" -batchmode -runTests -projectPath . -testPlatform EditMode -testResults test-results/editmode.xml'
  smoke: '"C:/Program Files/Unity/Hub/Editor/6000.3.26f1/Editor/Unity.exe" -batchmode -quit -projectPath . -logFile -'
```

> **如果编辑器不在 `PATH` 中，还要写入 `engine.path`。** Agent 和
> `/smoke-check` 读取它来查找编辑器，但命令按原样执行 —
> `engine.path` 从不会在运行时拼接到 `commands.*` 中，这就是为什么
> 完整路径要写入上面的命令 — 而在 Windows 和 macOS 上，
> 三个引擎默认都不会安装到 `PATH`（在 macOS 上编辑器位于应用
> 包内，例如 `/Applications/Godot.app/Contents/MacOS/Godot`）。询问或探测
> 安装位置并记录它 — Godot 和 Unity 记录编辑器可执行文件，
> Unreal 记录引擎文件夹（`<UE root>`）：
>
> ```yaml
> engine:
>   path: "C:/Program Files/Epic Games/UE_5.8"   # omit if the editor is on PATH
> ```
>
> **这并非表面功夫。** 没有它，agent 会报告*"这台机器上没有编辑器"*
> 并交付从未编译过的 C++ — 而实际上那台机器**确实**安装了该引擎。
> 项目中没有任何东西告诉它去哪里找，因此路径的缺失
> 被读成了引擎的缺失。

对于 **Unreal**，UE 的构建/测试命令因版本和项目设置而异。写入
尽力而为的值，并添加 `# TODO` 注释，让用户知道需要确认它们。
将 `<UE root>` 替换为引擎的安装文件夹（即你记录为
`engine.path` 的值）— 没有任何编辑器二进制文件在 `PATH` 中。这些命令包含
双引号，因此使用单引号标量。为项目开发所在的
机器编写该块（`uname -s`：`Linux`、`Darwin` = macOS，
其他 = Windows）。Windows 块已在 UE 5.7 上运行；Linux 和
macOS 行来自 Epic 的文档，连同其来源记录在
`docs/engine-reference/unreal/current-best-practices.md`（"Command Line"）中。

Windows：

```yaml
commands:
  # TODO: confirm these for your UE version and project — adjust via /settings
  build: '"<UE root>/Engine/Binaries/DotNET/AutomationTool/AutomationTool.exe" BuildCookRun -project="$(pwd -W 2>/dev/null || pwd)/<project>.uproject" -platform=Win64 -build -cook'
  test: '"<UE root>/Engine/Binaries/Win64/UnrealEditor-Cmd.exe" "$(pwd -W 2>/dev/null || pwd)/<project>.uproject" -ExecCmds="Automation RunTests <project>.; Quit" -unattended -nullrhi -stdout -FullStdOutLogOutput'
  run: '"<UE root>/Engine/Binaries/Win64/UnrealEditor.exe" "$(pwd -W 2>/dev/null || pwd)/<project>.uproject" -game -windowed -ResX=1280 -ResY=720'
  smoke: '"<UE root>/Engine/Binaries/Win64/UnrealEditor-Cmd.exe" "$(pwd -W 2>/dev/null || pwd)/<project>.uproject" -game -nullrhi -unattended -stdout -ExecCmds="Quit"'
```

Linux — 编辑器二进制文件是 `Engine/Binaries/Linux/UnrealEditor`，
构建脚本是 shell 脚本：

```yaml
commands:
  # TODO: confirm these for your UE version and project — adjust via /settings
  build: '"<UE root>/Engine/Build/BatchFiles/RunUAT.sh" BuildCookRun -project="$(pwd -W 2>/dev/null || pwd)/<project>.uproject" -platform=Linux -build -cook'
  test: '"<UE root>/Engine/Binaries/Linux/UnrealEditor" "$(pwd -W 2>/dev/null || pwd)/<project>.uproject" -ExecCmds="Automation RunTests <project>.; Quit" -unattended -nullrhi -stdout -FullStdOutLogOutput'
  run: '"<UE root>/Engine/Binaries/Linux/UnrealEditor" "$(pwd -W 2>/dev/null || pwd)/<project>.uproject" -game -windowed -ResX=1280 -ResY=720'
  smoke: '"<UE root>/Engine/Binaries/Linux/UnrealEditor" "$(pwd -W 2>/dev/null || pwd)/<project>.uproject" -game -nullrhi -unattended -stdout -ExecCmds="Quit"'
```

macOS — 只有构建有来源依据。Epic 记录了 `UnrealEditor.app`
包，但其中没有命令行编辑器，因此写入 `build`，其余三个保留为 TODO 行，
而不是猜测路径；在用户设置 `commands.test` 之前，`/smoke-check` 会将测试报告为
NOT ASSESSED：

```yaml
commands:
  # TODO: confirm this for your UE version and project — adjust via /settings
  build: '"<UE root>/Engine/Build/BatchFiles/RunUAT.sh" BuildCookRun -project="$(pwd -W 2>/dev/null || pwd)/<project>.uproject" -platform=Mac -build -cook'
  # TODO: test, run and smoke — no documented command-line editor on macOS.
  # Set them via /settings to the editor command you run for this project.
```

在 Windows 上，`build` 直接调用 AutomationTool：从 Git Bash 中，只要
项目路径含空格，`RunUAT.bat` 就会失败
（`'C:\Program' is not recognized`）。
AutomationTool.exe 在机器的 .NET 8 运行时上运行；`RunUAT.bat` 自带
SDK，因此当路径中没有空格且未安装 .NET 8 时，使用它。
`-build` 也会构建编辑器目标（已在 5.7 上验证）。

**三个细节至关重要。** 项目路径是绝对路径：UE 5.7
找不到相对路径的 `<project>.uproject`，会在任何东西运行之前以 1 退出
（`Project file not found`）。`$(pwd -W 2>/dev/null || pwd)` 在 Git Bash 中给出 `C:/…`
形式，在其他环境中给出普通路径，需从项目根目录运行；
仅用 `$PWD` 在设置了 `MSYS_NO_PATHCONV` 时会失败。`smoke` 需要 `-game`：没有它，
`UnrealEditor-Cmd` 启动的是*编辑器*，而在其中裸 `Quit` 控制台命令只能
结束播放模式（play-in-editor）会话 — 进程会驻留，命令
永不返回；加上 `-game`，同一行会无头启动并在几秒内退出。
`test` 需要在 `Automation` 字符串中包含 `; Quit`：自动化
运行器会自行处理末尾的 `Quit`，并在测试
完成后退出编辑器，没有它运行同样永不返回。其过滤器会运行全名*包含*
`<project>.` 的所有测试 — 是子串匹配，不是前缀匹配 — 因此
像 `qa-tester` 那样将测试命名为 `<project>.[System].[Scenario]`。如果
项目名称也是某个引擎领域 — `Audio`、`Core`、`Input`、`Test`、
`System`、`Engine`、`Editor`、`AI`、`Math` — 那么 `<project>.` 也会运行数百
到数千个引擎自身的测试；给测试一个不同的根（比如
`<project>Game.`），并在过滤器中放入相同的根。此形式在测试失败
以及过滤器匹配不到任何内容时都会以 255 退出（`No automation tests
matched`，已在 5.7 上验证），因此 `/smoke-check` 读取输出，而不是退出
码。`smoke` 出于同样原因带有 `-stdout`：没有它，启动失败
不会打印任何内容。不要换成
`-TestExit="Automation Test Queue Empty"`：除非解析其报告 JSON，
该形式在测试失败时会以 **0** 退出。

### 5.5.2 将块写入 `project.yaml`

向用户展示完整的四个块并询问：

> "我可以把 `engine`、`specialists`、`naming` 和 `commands` 块写入 `project.yaml` 吗？"

等待确认，然后根据文件当前状态执行：

- **`project.yaml` 不存在** — 使用 Write 工具按此
  v1.1 模板创建它（四个块追加在 `framework` 之后；替换 `<...>` 和
  日期）：

  ```yaml
  # CCGS project configuration — single source of truth for project settings.
  # Schema: grep the `## <key>` section of .claude/docs/effects-map.md —
  # it is ~31k tokens whole, ~900 per section. Do not open it entire.

  schema_version: 1

  framework:
    version: 1.2.0
    last_upgraded: <today's date>

  engine:
    name: "<...>"
    version: "<...>"
    language: "<...>"
    rendering: "<...>"
    physics: "<...>"

  specialists:
    code: "<...>"
    shader: "<...>"
    ui: "<...>"
    additional: ["<...>"]

  naming:
    classes: <...>
    variables: <...>
    constants: <...>
    signals: <...>
    files: <...>
    scenes: <...>

  commands:
    build: "<...>"
    test: "<...>"
    run: "<...>"
    smoke: "<...>"
  ```

  不要在这里预置 `modes.review_mode`。它是一个以严谨度为前置的开关 — `modes.rigor`
  提供其值，因此显式值会遮蔽严谨度展开，并固定
  评审模式，无论项目的严谨度如何。

- **`project.yaml` 存在** — 先 Read 它（Edit 工具要求在本会话中
  已读取该文件），然后按 `engine` → `specialists` → `naming` → `commands`
  的顺序处理各块，对每个块：
  - **块不存在** — 插入整个块，追加在最后一个现有
    顶层块之后。
  - **块已存在**（重新运行 `/setup-engine`）— 就地编辑现有
    键，并补上块中缺失的任何键（不完整的块最终必须
    拥有完整的键集）。不要添加该块的第二份副本。

**macOS 上的 Unreal 在两种情况下都是例外：** `commands.test`、`run` 和
`smoke` 按 macOS 块中的 TODO 注释行写入 — 绝不要写成
`<...>` 占位符或猜测的路径 — 并且在用户设置它们之前，重新运行会让它们保持未设置。

保留 `project.yaml` 中的所有其他内容（`schema_version`、`framework`、
`modes`、`project` 等）— 只改动这四个块。

### 5.5.3 验证双写

回读 `project.yaml`，确认四个块存在，且
`engine.name`、`engine.language` 以及命名值与写入
`technical-preferences.md` 的内容一致。如果它们有分歧，向用户报告差异
并停止 — 配置分裂会破坏技能和钩子的读取。
